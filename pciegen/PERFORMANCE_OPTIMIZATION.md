# PCIe 生成工具性能优化结果

日期：2026-10-11。已修改本地 `pciegen`、`vutils` 和 `ramgen` 源码；Verible 可执行文件保持原版本。

主要收益来自减少重复工作。调用关系是 `pciegen → vutils → verible-verilog-syntax.exe`，以及 `pciegen → ramgen`。Verible 自身不会调用这两个 Python 工具。

## 不到十个文件、每个两三千行的使用规模

用户进一步说明实际工程不到 10 个文件，每个约 2,000–3,000 行。新增两组对应规模的合成输入：7 个 SV 文件，外加两个编译清单，所有 SV 文件都增加相应数量的声明，包含 15 个相同配置的 RAM。每组在独立 Python 进程中重复三次，使用当前优化后的代码。

| 场景 | 总耗时，秒 | RTL 编辑，秒 | wrapper 生成，秒 | ramgen，秒 | 准备，秒 |
|---|---:|---:|---:|---:|---:|
| 7 个 SV，每个约 2,000 行 | 2.2147 | 1.7558 | 0.1783 | 0.0279 | 0.2503 |
| 7 个 SV，每个约 3,000 行 | 3.0431 | 2.4062 | 0.2572 | 0.0344 | 0.3525 |

RTL 编辑阶段约占总耗时 79%，ramgen 阶段约占 1%。Verible 子进程的累计时间约 1.05 / 1.39 秒，包含启动、解析、JSON 序列化和输出；这不能当作纯语法分析耗时。累计 JSON 输出约 57.96 / 86.33 MB。剩余时间包含 Python 的 JSON 解码、节点构造与遍历，以及文件操作等。

此规模的优化重点明确：减少同一文件重复生成完整 CST、复用有效接口元数据、减少只读取端口时的整树节点构造。RAM 数量和文件数量都较少，大量 RAM 改写和大量小文件复制不应作为后续主攻方向。准备阶段还包含模块前缀检测的完整解析，不能将该列全部算作复制耗时。

这些合成文件主要使用简单声明扩充行数；真实 RTL 中实例、表达式、宏和 generate 结构会改变解析及遍历成本。表中时间也不含解释器启动与依赖导入，因此不能直接视为用户真实工程的完整命令耗时。

脚本场景：`user_scale_2000`、`user_scale_3000`。原始数据：`test/pipeline_user_scale_measurements.json`，其中记录了每个 SV 文件的实际行数。未据此宣称新的生产优化收益；本次补充仅新增测量场景和记录。

## 十几个 RAM 的使用规模

根据用户补充的实际 RAM 数量，新增固定 15 个 RAM 的四组场景，各重复三次取中位数，使用当前已优化的代码。RAM 使用同一参数配置，生成一种 reference wrapper；其他输入规模仍是合成的，不能代表真实工程的精确耗时。

| 场景，均为 15 个 RAM | 总耗时，秒 | ramgen，秒 | RTL 编辑，秒 | wrapper 生成，秒 | 准备，秒 |
|---|---:|---:|---:|---:|---:|
| 五个目标模块各附加 100 行 | 0.3183 | 0.0088 | 0.2341 | 0.0342 | 0.0404 |
| 五个目标模块各附加 2,000 行 | 1.7611 | 0.0087 | 1.3654 | 0.1948 | 0.1928 |
| 五个目标模块各附加 10,000 行 | 9.6383 | 0.0112 | 7.4167 | 1.1127 | 0.9734 |
| 附加 2,000 个小文件 | 2.1134 | 0.0102 | 0.2606 | 0.0315 | 1.7880 |

该规模下，ramgen 阶段仅约 9–11 毫秒，占全流程约 0.12%–2.76%，其中 RAM 类型改写约 2–3 毫秒。继续压缩这部分对总耗时的收益有限。之前 1,000 RAM 场景的全流程加速倍数属于大量实例的压力测量，应按实际数量选择对应场景。

后续优先级：同一 RTL 文件的修改进一步合并、wrapper 复用有效接口分析结果、减少端口读取时完整语法树的构造；文件较多时，再优化复制及权限遍历。RAM 数量少也不保证 RAM 源文件很小，提取接口仍可能受该文件内其他逻辑的规模影响。

新增脚本场景：`ram_15`、`ram_15_body_2000`、`ram_15_body_10000`、`ram_15_files_2000`。原始数据：`test/pipeline_ram_15_measurements.json`。阶段中位数分别计算，不能要求各列精确相加等于总耗时。

## 已实施的优化

1. **多模块文件一次解析后选择目标。** `vedit.from_file(auto_select=True, inst_name=...)` 从已有 CST 中查找实例归属，随后按文件名或首个模块回退。默认 `from_file()` 仍拒绝未指定目标的多模块文件。候选数量不再增加 Verible 启动次数。
2. **模块端口和实例连线合为一个事务。** 新增 `add_ports_and_inst_ports()`，复用原始 CST，先修改实例连线，再修改其前面的端口列表和非 ANSI 声明，最后统一检查语法。冲突或语法错误会恢复原文。`pciegen._append_to_file()` 已接入。
3. **按需提取实例。** 首次读取端口、参数或模块风格时只计算相关元数据；读取实例或编辑实例时，在已缓存的 CST 上补充实例信息。`analyze(include_instances=False)` 复用缓存。
4. **减少 Python 树遍历开销。** 深度优先遍历改为显式栈；避免逐节点复制子节点列表，并预先处理筛选条件。保持前序、后序及反向子节点顺序。
5. **RAM 类型改写使用统一范围表。** 一次分词，线性配对括号，根据类型和实例名称定位替换范围，然后统一拼接输出。跳过注释和字符串，支持嵌套参数括号及实例数组，保留其余原文。
6. **字典索引与集中拼接。** wrapper 同名端口查询使用字典；批量实例编辑一次建立实例和 CST 节点索引；多个不重叠文本修改统一组装，避免逐修改复制整份最终文本。

## 完整流水线前后对比

沿用原有合成输入、计时边界和本地工具。每个场景在独立 Python 进程中运行真实五步 `pciegen.run()`，重复三次，报告中位数。时间不包含解释器启动、依赖导入、输入构造、测试后检查与临时目录清理。具体方法见 `PERFORMANCE_REVIEW.md`。

| 场景 | 优化前，秒 | 优化后，秒 | 加速倍数 |
|---|---:|---:|---:|
| 基础场景 | 0.4954 | 0.3088 | 1.60× |
| 五个目标模块各增加到 2,000 行 | 2.7443 | 1.6691 | 1.64× |
| 五个目标模块各增加到 10,000 行 | 14.9206 | 9.0454 | 1.65× |
| 100 个 RAM 实例 | 0.5984 | 0.4089 | 1.46× |
| 500 个 RAM 实例 | 1.3277 | 0.7632 | 1.74× |
| 1,000 个 RAM 实例 | 2.9035 | 1.2341 | 2.35× |
| cdm.sv 内 16 个模块，目标位于最后 | 0.8926 | 0.3137 | 2.85× |
| cdm.sv 内 64 个模块，目标位于最后 | 2.4485 | 0.3293 | 7.44× |
| 1,000 个附加端口 | 1.1494 | 0.7543 | 1.52× |
| 2,000 个附加小文件 | 2.2083 | 2.0581 | 1.07× |
| 相同文件已完整存在于 rtl 中 | 2.2802 | 2.0832 | 1.09× |

基础场景的五个模块各有 100 行附加声明、32 个附加 subsystem 端口及 1 个 RAM。各扩展场景只改变对应维度。这些数据反映本机合成输入，不能直接当作真实项目的耗时或加速承诺。

普通流程 Verible 调用 **22 → 14 次**，完整 CST 导出 **13 → 9 次**。多模块 16 / 64 的场景从 40 / 88 次降至相同的 14 次。每次实际修改仍保留语法检查；幂等的批量编辑不额外调用验证。

10,000 行场景累计 JSON 输出从 **380.30 MB → 253.53 MB**。Python 峰值工作集约 **210.0 → 204.2 MiB**，下降较小；此轮主要改善时间，没有消除完整 CST 的内存开销。工作集不包含 Verible 子进程。

## 局部测量

`ramgen.generate_output_sv()`：

| RAM 实例数 | 优化前，秒 | 优化后，秒 |
|---|---:|---:|
| 100 | 0.0206 | 0.0053 |
| 500 | 0.3759 | 0.0206 |
| 1,000 | 1.4113 | 0.0623 |

1,000 实例时，RAM 类型改写约快 **22.7 倍**，整个 ramgen 阶段降到约 0.122 秒。完整流程的收益更小，因为读取 RAM 接口仍需要导出、解码和构造完整语法树。

隔离初始解析的通用编辑测量：编辑 400 个实例中的 100 个，**0.6238 → 0.0265 秒**，每轮仍只调用一次语法检查。隔离 CST 的 8,000 端口 wrapper 映射/输出，**1.0037 → 0.3474 秒**。这些局部测量不能替代上面的全流程结果，小场景会受到系统调度和文件写盘波动影响。

## 验证

55 项目标回归测试通过：pciegen 20 项，vutils 批量编辑与解析 20 项，已有实例/宏实例 10 项，RAM 改写 5 项。覆盖：

- ANSI / 非 ANSI / 单行源码的合并编辑，与原有逐步编辑输出逐字一致；幂等编辑；错误回滚。
- 多模块目标选择只解析一次；端口读取延迟分析实例，后续实例读取不重新解析。
- 树遍历顺序、反向顺序和 1,500 层深度。
- 1,000 RAM 实例与旧改写算法输出逐字一致；嵌套参数、数组、注释、字符串、名称边界和重复实例名称。
- 前一轮已修复的别名、位宽、参数、RAM 端口及 flist 问题。

无 RAM 生成场景与真实 RAM 生成完整流程通过；后者对 11 个生成/编辑的 SV 文件完成 Verible 语法检查。`git diff --check` 通过。这些检查不包含硬件功能仿真，也不是整个仓库所有历史测试的运行结果。

## 下一轮应优先处理什么

1. **大文件：按文件进一步合并改写，传递已分析的接口结果。** 10,000 行场景仍花约 7.10 秒在 RTL 编辑、1.02 秒在 wrapper 接口解析。考虑仅需接口时减少完整树的 Python 构造，并让同一文件后续步骤复用有效结果。任何缓存必须与源码版本绑定，修改后不能继续使用旧偏移。
2. **多小文件：减少复制及权限遍历。** 2,000 文件场景的准备阶段仍约 1.77 秒，占总时间约 86%。只在必要时解除只读，源与目标内容可靠相同时跳过复制。已被上一轮改写的目标文件必须从源恢复，不能仅凭源时间戳跳过。
3. **再考虑独立文件的并行处理。** 应先降低解析次数和 JSON 量。当前完整语法树的峰值内存仍高，盲目并行会叠加内存开销。
